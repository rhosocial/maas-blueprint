# 第 1 章 MaaS 是什么、不是什么

> MaaS 卖的不是 GPU，也不是一个 OpenAI 兼容的 URL，而是**可计量的模型能力 + 可承诺的服务等级**。

## 1.1 三层定义

把 MaaS 拆成三层，每层有自己的客户和失败方式：

| 层 | 交付物 | 直接客户 | 成功指标 | 失败表现 |
|---|---|---|---|---|
| 算力底座 | GPU、网络、存储、调度 | 平台团队 | 利用率、故障间隔、恢复时间 | 卡在空转，或一坏一片 |
| 推理平台 | 副本、引擎、路由、任务执行 | 业务/产品 | 单位 token 成本、TTFT、任务完成率 | 能跑但扩不动、一发布就掉线 |
| 产品化运营 | 目录、API、租户、计量、账单、SLA、合规 | 外部客户 | 收入、留存、毛利、投诉率 | 技术很好但收不到钱、过不了审 |

三层都成立才叫 MaaS。只有第一层是 GPU 租赁，只有第二层是内部推理服务，
只有第三层是 API 转售。**三层之间的耦合点只有三个契约**：部署规格、任务契约、计量事件。

## 1.2 与相邻形态的边界

| 形态 | 客户买到什么 | 是否承担 SLO | 是否按请求计量 | 是否负责内容合规 | 是否管模型生命周期 |
|---|---|---|---|---|---|
| GPU 租赁（IaaS） | 裸卡/裸机 | 基础设施可用性 | 否（按卡时） | 否 | 否 |
| 模型托管（PaaS） | 一个可调用的模型端点 | 部分 | 部分 | 通常转移给客户 | 部分 |
| API 转售/聚合 | 上游模型的转发 | 上游决定 | 是 | 通常不承担 | 否 |
| **MaaS（本书）** | 模型能力 + 等级 + 账单 + 合规背书 | **是** | **是** | **是（服务提供者）** | **是** |

判断一家公司做的是不是 MaaS，看四个问题就够了：

1. 客户能不能拿到**书面 SLO**，做不到时有没有赔付？
2. 能不能按请求/ token / 张 / 秒**开出账单**，并解释每一笔？
3. 生成内容出问题时，**谁承担审核与标识责任**？
4. 模型换版本、换引擎、换量化时，**客户代码要不要改**？

四个都答"是"，才是产品；有一个答"不"，就还是项目。

## 1.3 自建还是用云

这不是一个二选一，而是一个**分层选择题**：

| 维度 | 自建 | 云托管 | 蓝本建议 |
|---|---|---|---|
| 单位成本（稳态） | 低，但要求高利用率 | 高，但随用随付 | 稳态自建，峰值溢出到云 |
| 引擎/网络控制力 | 完全 | 受限于厂商 | 控制面自持，数据面可混合 |
| 合规（备案主体、数据位置） | 自己承担，路径清晰 | 责任界面模糊 | 对外售卖必须自己备案 |
| 上市时间 | 慢（3~6 个月起步） | 快（周级） | 先用云验证需求，再迁稳态 |
| 运维人力 | 高（SRE + 平台） | 低 | 人力是最容易被低估的成本 |
| 供应链风险 | 卡、备件、驱动 | 厂商锁定 | 保留第二来源 |

〔建议〕**控制面必须自持，数据面允许混合。** 理由：目录、计量、账单、租户、合规记录
是资产和责任的载体，不能放在别人的 API 后面；而 GPU 可以按成本在自建与云之间调度。

一个反直觉的结论：**自建不一定更便宜**。当利用率低于某个阈值（经验上 40%~50%，
需按实际采购价重算）时，自建的单卡时成本会高于云价，因为闲置、备件、人力和机房
都被摊到了有效卡时上。第 03 章把这个账算清楚。

## 1.4 五条成功判据

每条都给一个可执行的验收动作，避免"感觉做完了"：

| 判据 | 验收动作 | 不通过的样子 |
|---|---|---|
| 能跑 | 单副本压测达到规格卡的 80% 吞吐 | 只能 demo，一压就超时 |
| 能交付 | 视频任务在实例被 kill 后仍能完成 | 实例一挂任务就丢 |
| 能卖 | 能从下单到出账单全链路走通（含退款） | 账单靠 Excel |
| 能算账 | 能算出每个模型、每个租户的单位成本 | 只知道总电费 |
| 能过审 | 附录 C 的检查清单全部闭合 | 上线前两周才发现要备案 |

## 1.5 本书范围

| 在范围内 | 不在范围内 |
|---|---|
| 推理平台架构、调度、弹性、发布 | 训练算法与模型结构 |
| 多模态数据面与任务系统 | 具体推理引擎的源码改造细节 |
| 计量、计费、限流、SLA | 商务合同、渠道政策 |
| 合规的工程落地 | 法律意见（只给工程约束） |
| 容量与成本模型 | 采购谈判 |

## 1.6 五个常见误判

1. **"OpenAI 兼容 = MaaS"**。兼容只解决接入，不解决计量口径、失败退款、长任务交付和合规。
2. **"有 GPU 就有平台"**。没有部署规格和副本抽象，扩容时只能手工改 YAML。
3. **"模型效果好就能卖"**。企业客户先问 SLA、数据怎么处理、出了事谁负责，再问效果。
4. **"先上线再补合规"**。备案周期以月计，标识与审核必须长在管线里，后补等于重构。
5. **"按 token 计价就完事"**。缓存命中、长上下文、失败重试、视频秒数，都会让单一计价单位失真。

## 本章结论

- MaaS 的产品边界由**责任**划定：承担 SLO、计量、合规，才是 MaaS。
- 自建与云不是对立选项；**控制面自持、数据面混合**是更稳的起点。
- 五条成功判据必须在第一版就定义，否则后续所有优化都缺少验收标准。

## 决策点（结合自身情况）

1. 团队是否接受"承担内容合规责任"？这决定第 33~35 章是否是 P0。
2. 首个商业化形态是"按量 API"还是"承诺吞吐 + 专属部署"？两者对架构要求不同。
