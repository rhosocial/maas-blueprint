# 第 20 章 LLM 数据面

> OpenAI 兼容是入场券，不是差异化。真正决定体验的是流式细节、错误语义和取消传导。

## 20.1 最小端点集合

| 端点 | 用途 | 是否必须 |
|---|---|---|
| `GET /v1/models` | 列出可用模型与能力 | 必须 |
| `POST /v1/chat/completions` | 对话/生成 | 必须 |
| `POST /v1/embeddings` | 向量化 | 视业务 |
| `POST /v1/completions` | 旧版补全 | 兼容可选 |
| `POST /v1/files` | 批量输入 | 批量时需要 |
| `POST /v1/batches` | 异步批量 | 批量时需要 |

`/v1/models` 不能只返回名字，要返回能力元数据：

```json
{
  "id": "llm-pro",
  "object": "model",
  "owned_by": "platform",
  "context_window": 32768,
  "max_output_tokens": 8192,
  "modalities": ["text"],
  "capabilities": ["chat", "tools", "json_mode", "stream"],
  "version": "2026-10-01",
  "deprecated_at": null
}
```

客户据此做路由与降级，不需要读文档猜。

## 20.2 SSE 的七个坑

| 坑 | 现象 | 解决 |
|---|---|---|
| 代理缓冲 | 客户端收不到增量，最后一次性吐出 | 关闭缓冲（如 `X-Accel-Buffering: no`） |
| 压缩 | 小 chunk 被合并 | 流式响应禁用 gzip |
| 超时 | 长生成被中间层断开 | 逐层调大读超时 |
| 心跳缺失 | 空闲被 LB 断开 | 每 15~30 秒发注释行 `: ping` |
| 结束符 | 客户端不知道结束 | 发 `data: [DONE]` |
| 错误 mid-stream | 无法用 HTTP 状态码表达 | 发 `event: error` + 结构化 body |
| 连接复用 | 多路复用导致串流 | 每请求独立连接 |

流式响应的最小骨架：

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

data: {"id":"...","choices":[{"delta":{"content":"你"}}]}

data: {"id":"...","choices":[{"delta":{"content":"好"}}]}

data: [DONE]
```

## 20.3 工具调用与结构化输出

| 能力 | 难点 | 建议 |
|---|---|---|
| 工具调用 | 流式下参数是分片的 JSON | 累积后解析，最后校验 schema |
| 结构化输出 | 强约束 vs 后处理 | 优先引擎原生约束解码 |
| 并行工具调用 | 顺序与 ID 对应 | 用 `tool_call_id` 关联结果 |
| 解析失败 | 模型输出非法 JSON | 有限重试 + 明确错误码，不静默截断 |

一个常见事故：流式返回的 `arguments` 是逐字符拼接的，客户端在中途解析必然失败。
文档里必须写清"累积到 `finish_reason=tool_calls` 后再解析"。

## 20.4 多模态输入

| 方式 | 适用 | 注意 |
|---|---|---|
| URL（对象存储） | 大文件、视频 | 预签名有效期要覆盖处理时间 |
| base64 内联 | 小图 | 请求体膨胀 33%，限制大小 |
| 上传后引用 | 多轮复用 | 需要文件生命周期管理 |

〔建议〕**大于 1MB 的输入一律走 URL，不走 base64。** 否则网关内存和日志都会被撑爆。

## 20.5 错误语义

| HTTP | 场景 | 客户端应做什么 |
|---|---|---|
| 400 | 参数错误 | 修正，不重试 |
| 401/403 | 鉴权/权限 | 换 Key，不重试 |
| 404 | 模型不存在/已下线 | 换模型 |
| 413 | 请求过大 | 减小输入 |
| 422 | 内容审核拒绝 | 修改内容，不重试 |
| 429 | 限流/配额 | 按 `Retry-After` 重试 |
| 500 | 平台内部错误 | 可重试（有预算） |
| 503 | 过载/无可用副本 | 可重试（有预算） |
| 504 | 超时 | 视情况，流式不重试 |

错误体要统一：

```json
{
  "error": {
    "code": "rate_limit_exceeded",
    "message": "...",
    "type": "rate_limit_error",
    "request_id": "...",
    "retry_after_ms": 1200
  }
}
```

`request_id` 必须返回，否则客户报障时无法定位。

## 20.6 取消与计量

- 客户端断开 → 网关检测 → 取消上下文 → 引擎停止生成 → 按已生成 token 计量。
- 取消不是"免费"：已经消耗的算力要计费，但可以按"已生成 token"而非"最大 token"。
- 计量事件在连接关闭时兜底上报，不能只依赖正常结束。

## 20.7 契约与版本

| 变更 | 是否兼容 | 处理 |
|---|---|---|
| 新增可选字段 | 兼容 | 直接发 |
| 新增枚举值 | 可能不兼容 | 提前公告 |
| 修改默认值 | 不兼容 | 新版本 |
| 删除字段 | 不兼容 | 弃用周期 ≥ 6 个月 |
| 修改错误码 | 不兼容 | 新版本 + 映射表 |

## 本章结论

- `/v1/models` 要带能力元数据，客户才能做路由与降级。
- SSE 的坑主要在中间层（缓冲、超时、心跳），不在应用代码。
- 工具调用的流式参数必须累积后解析。
- 大输入走 URL，错误体必须带 `request_id`。

## 决策点（结合自身情况）

1. 是否支持 `/v1/completions` 旧接口？维护成本与客户兼容性取舍。
2. 结构化输出用引擎原生还是后处理？
3. 单请求最大输出长度与超时定多少？
