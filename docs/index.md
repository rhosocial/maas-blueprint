# MaaS Blueprint

> 商业化多模态 MaaS 的参考蓝本：从 GPU 集群到可售卖的服务。

- 版本：v0.1（2026-10-27）
- 状态：初稿完成，持续修订
- 许可：文档 CC BY 4.0；代码示例 Apache-2.0（见 [LICENSE](https://github.com/rhosocial/maas-blueprint/blob/main/LICENSE)）

> **这是蓝本，不是规范。**
> 书中的架构、参数、价格、流程都是参考解，不是必须遵守的标准。每个团队应结合自己的
> 客户结构、成本、合规属地、团队规模做决策。书中的数字用于校验数量级，不是报价或承诺。

## 1. 这份蓝本解决什么问题

把“能跑推理”变成“能对外售卖的多模态 MaaS”，中间隔着四件事：

| 层 | 问题 | 对应篇章 |
|---|---|---|
| 能跑 | GPU 怎么分、副本怎么起、请求怎么进 | 第二、三、四篇 |
| 能交付 | 长任务怎么不丢、失败怎么重试、结果怎么送达 | 第五、六篇 |
| 能卖 | 模型怎么上架、怎么计量、怎么限流、怎么承诺 SLA | 第七篇 |
| 能长期卖 | 合规、安全、成本、故障、组织 | 第八、九篇 |

一句话立场：**MaaS = 推理平台 + 产品化运营层。前者决定毛利的下限，后者决定能不能收到钱。**

## 2. 参考场景与假设

蓝本按以下场景写作。**这些是默认值，不是前提条件**；换成别的场景时，相关章节要重算。

1. **对外售卖**，不是内部共享平台。因此计费、SLA、合规、租户隔离都是一等公民。
2. **模型自研 + 多模态**（文本 / 图像 / 视频）。因此要自己做引擎适配，且自己就是备案主体。
3. **中国大陆合规环境**。备案、生成内容标识、内容审核按当地监管口径设计。
4. **Kubernetes 为底座**，单集群千卡量级起步，可扩展到多集群。
5. **团队规模有限**（平台 + 引擎 + 产品 + 合规合计数十人）。这决定了书中反复出现的取舍：
   **能买的不自研，能晚做的不早做**。

如果你的场景是“只做文本”“只做内部平台”“只做海外市场”，书中的部分结论会失效。
每章开头会尽量写明前提；没有前提的结论，请视为不可直接复用。

## 3. 三条主线

1. **三个契约**：部署规格、任务契约、计量事件。所有分层都围绕它们，
   避免“每加一个模态就改一遍计费”。
2. **四个资源池 + 一条借还通道**：LLM 在线、图像、视频、批处理；
   借卡必须满足“可中断、可快速归还、可硬隔离”。
3. **合规先行**：备案、标识、审核不是上线前手续，而是架构约束；
   审核与标识故障时**拒绝服务，不降级放行**。

## 6. 事实分级

书中混有三类内容，**不区分就会把观点当事实**：

| 标记 | 含义 | 怎么用 |
|---|---|---|
| 〔建议〕 | 蓝本给出的参考选择 | 可以采纳，也可以推翻；推翻时记 ADR |
| 〔通行〕 | 业界当前通行做法 | 会随版本演化，落地前按当期文档复核 |
| 〔核验〕 | 外部事实（法规、项目版本、第三方条款） | **上线、签约或对外承诺前必须核对原始来源** |

具体的外部事实统一登记在 [附录 E](附录/E-待核验清单.md)，包括“如果这条不成立，会影响什么”。

## 7. 怎么把蓝本变成决策

不要从头读到尾再动手。建议按“每章一个交付物”推进：

1. 读完 01~05，产出一页纸定位、资源池图、架构图、合规约束表。
2. 每读完一篇，把该篇的「决策点」抄进自己的决策清单，开会拍板并记 ADR。
3. 附录 C 的检查清单直接作为上线 gate，不通过不上线。
4. 附录 E 的核验项指定责任人和截止时间，逾期视为风险升级。

书中的 ADR 编号、阶段划分、指标阈值都是**示例**。替换成你们自己的编号体系，比照搬更有价值。

## 8. 不写什么

- Kubernetes 入门、推理引擎源码解析、商务合同模板、具体厂商评测。
- 训练算法与模型结构（训练平台只作为推理平台的底座出现）。
- 法律意见。合规章节只给工程约束，具体条款请咨询法务或主管部门。
